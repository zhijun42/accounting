# Accounting

一个为个人生活梳理而设计的本地记账工具。通过关联支付宝、微信、美团和工商银行借记卡的记录，理解每个月实际参与的活动与个人承担的消费。

当前分析目标为 **2026 年 4 月 1 日至 9 月 30 日**。美国银行信用卡消费不纳入本项目。

## 目标架构与运行 workflow

**AI Agent 负责逐笔阅读、理解和判断；Python 后端负责提供数据、执行明确的修改并记录审计；本人通过 UI 核对和补充。** 本项目不是用 hard-coded rules 替代 AI 理解的自动分类或匹配系统。以下描述目标工作方式，不表示现有代码已经全部符合这一架构。

1. **导入并保留原始证据。** Python 解析各渠道文件、规范日期和金额，并利用可靠的渠道内交易 ID 等信息进行同源去重，保存到 `raw_records`。导入不推断消费类别，也不把不同渠道的记录自动认定为同一笔消费。
2. **向 AI 提供待检查记录及上下文。** AI 按本人指定的范围逐笔读取账单，结合关联或可能相关的原始流水、订单信息、分类树、修改历史和本人的分类偏好。后端提供只读查询与筛选；初次试评的 200 条只是一个批次，不是产品的总处理上限。
3. **由 AI 使用 LLM 能力作出业务判断。** 判断这是什么消费、原类别是否合理、哪些来源描述同一次支付、哪些只是内部资金移动。支付宝原分类正确则保留；错误或缺失则根据证据纠正、补充。依据充分时可直接执行，有歧义时记录原因及需要本人回答的问题，不以猜测填满类别。
4. **通过轻量后端落库和留痕。** AI 提交针对具体记录的明确决定，包括要改的字段、关联或归并对象、理由和来源证据。Python 在事务中执行，记录执行者、修改前后值、理由及证据引用；原始流水不可改写。保留原分类或暂时无法判断，也要记录已经检查及其结论，不能只记录发生了字段修改的记录。
5. **由本人在 UI 中 review。** 展示整理后的消费、AI 判断理由、原始证据和修改历史，区分“AI未检查待核对”“AI已检查待核对”和本人已确认。本人可以修改标题、大小类，填写使用日期并回答疑问；人工保存的修改受到保护，即使尚未点击确认，也不应被后续 AI 判断自动覆盖。AI 已检查不等于本人已确认。

### AI 的判断原则

- **消费分类是语义判断。** 每笔消费最终必须有明确的大类，小类可选，允许本人自定义，不使用“其他”兜底。“待分类”是尚未完成判断的状态，不是消费类别。本人的分类偏好是提供给 AI 的上下文，不应被编译成关键词分类规则。
- **跨渠道记录只反映一次真实支出。** 美团通常提供商品或活动信息，支付宝、微信及借记卡提供支付或扣款信息。AI 综合订单号、商品、商户、时间、金额、渠道和上下文判断关联，保留可追溯的来源，而不是将多份流水金额相加。已匹配的美团消费优先采用美团中有意义的商品或活动名称；本人修改的标题优先保留。
- **允许理解一对多和资金链。** 一次付款可能对应商品与券包等多条美团记录；单条金额不相等不意味着不能归并。本人账户间的筹款、提现、转入等应与最终消费区分，不重复计费。小额差异本身既不是拒绝关联的充分理由，也不是自动合并的充分理由；AI 需综合证据，并如实保留未解释的差异，不能凭推测新增手续费消费。
- **产品以消费为主。** 收入和已识别的本人账户间资金移动保留原始证据，但不作为消费展示和统计。退款、垫付归还不能仅因资金入账就当作普通收入，需要结合相关消费理解。
- **尊重本人提供的信息。** 使用日期由本人填写，AI 不推断演出或活动的实际日期；年卡、多次课暂按单笔记录，不自行分摊，也不自动推断本人承担金额。

### Python 的职责边界

后端可以做文件解析、同源去重、只读检索、明确修改的执行、备份和审计，以及必要的数据完整性与安全校验：例如记录和类别是否存在、版本是否过期、是否覆盖人工修改、关联是否形成循环、事务是否完整。

后端不应靠商户关键词、固定时间窗口、金额必须完全相等或“匹配组合必须唯一”等业务规则，代替或否决 AI 对具体账单的理解。查询可以帮助定位证据，但查询范围不能变成认定关联的硬性门槛；证据不足由 AI 说明并交给本人核对。

当前对话中的 AI Agent 就是执行阅读和判断的 LLM，不要求 Python 再调用一次模型 API，也不要求引入无人复核的后台分类服务。若使用 JSON 计划，它只是这一批具体判断的执行载体，不是可反复套用的分类规则库；私有偏好、计划和报告只保存在 Git 忽略的本地目录。

## 本地运行

需要 Python 3.11+，以及 Python 自带的 SQLite 3.38+（含 JSON 函数）。前端开发和首次构建还需要 Node.js 22.13+（22.x）、24.x 或 26+ 与 npm，建议使用 Node.js 24 LTS。安装依赖后不需要网络即可导入或使用已构建的界面；导入命令不会调用 AI、上传数据或操作 Git。

```sh
python3 -m venv .venv
source .venv/bin/activate
python3 -m pip install -e .
make install-ui
make test
make import INPUT_DIR=. DATABASE=data/accounting.sqlite3
make stats DATABASE=data/accounting.sqlite3
make serve DATABASE=data/accounting.sqlite3 PORT=8765
```

启动后打开 `http://127.0.0.1:8765`；如果端口已被占用，可用 `PORT=8777` 换端口并打开对应地址。默认显示 2026 年 4—9 月、按支付日期筛选的全部记录，也可切换月份或全年。关闭终端中的服务时按 Ctrl+C；之后仍可用同一命令启动，修改保存在 SQLite 中。

当前 UI 的核对流程：

1. 搜索商品、商户或交易号，按平台、月份、资金性质、分类状态或核对状态筛选；每页 50 条。“待分类”只包括消费或性质待定且没有消费类别的记录，不包括收入、退款、转账等；可与 AI 检查状态组合。
2. 选择记录，在右侧查看平台原分类和原始字段；先判断是消费、退款、收入、转账等哪种资金性质。
3. 可修改消费标题（非空、最多 500 字），不改原始流水；修改前后标题记入审计历史。消费填写大类与可选小类、本人承担金额，以及可选的使用日期、备注。不确定时“保存修改”保留待核对状态。
4. “确认并下一笔”确认当前记录、保护人工分类，并进入下一条。修改已确认记录仍需满足完整分类和金额约束。
5. 在“分类管理”中添加大小类；在单笔详情或“修改记录”中查看执行者、理由和修改前后值。

待核对记录在侧栏、列表和详情中区分“AI已检查待核对”和“AI未检查待核对”，可直接点击侧栏筛选。AI 是否检查过取自不可变审计日志中 AI 新增的资金性质或消费分类判断，包括保留分类及信息不足的判断；不依据分类是否为空，也不把普通 AI 备注或匹配操作当作检查。本人确认后，该记录退出待核对列表，但历史检查记录保留。该标记表示曾经检查过，不保证后续改动已经被 AI 重新检查。此展示不改写 `bills.review_status`，不代替本人确认或绕过人工保护。

产品聚焦钱花在哪里，不展示收入。列表、搜索、侧栏计数、直接详情及全局修改记录均隐藏已识别的收入，原始流水、整理记录和审计日志不删除。除已标为 `income` 的账单外，仍为 `pending` 的来源明确收入也隐藏：支付宝成功的标准“余额宝-YYYY.MM.DD-收益发放”流水、支付宝原类别为收入且入账的流水，以及工行摘要明确为利息/结息的入账。规则只读取主原始来源，不依赖可编辑标题，不改写分类或 AI 检查状态。退款、垫付归还、未明用途的收款、提现到账及余额宝本金转出不会仅因入账或“投资理财”类别被隐藏。核对时可将一笔记录改为“收入（保存后隐藏）”，保存成功后退出列表；收入仍可在本地数据库审计。

已明确标为 `internal_transfer` 的本人账户间资金流转同样不展示；在编辑器标记后保存成功再退出列表。购买商品仍保留最终实际支付记录，筹款过程不硬合并为该笔消费、不改原始金额。资金链的小额未解释差额保留在证据中，不阻碍明确的最终支出只计一次，也不凭推测新增手续费消费。用途不明的转账及投资行为不会一概隐藏。

启动 UI 前会使用 SQLite 备份 API 在数据库旁的 `backups/` 目录保存副本。保存时检查记录版本，过期页面会返回冲突，不覆盖新的修改；可点击核对面板右上角刷新并重新填写。界面支持排除统计并填写原因；软删除、跨平台合并、退款/垫付分配及历史撤销暂未提供 UI 操作。

服务仅绑定 `127.0.0.1`，校验 Host、Origin 和写入令牌，禁止跨站访问；静态资源没有 CDN 或第三方脚本，响应不缓存。它不是多用户生产服务器，也没有加密本地数据库：同机用户或进程的文件权限仍需由操作系统管理，不应通过端口转发或隧道公开服务。

`make test` 依次执行 TypeScript 严格类型检查、前端生产构建、Python 测试与前端测试。也可单独运行 `make check-ui`、`make build-ui`、`make test-python`、`make test-ui`；HTTP 静态资源测试需要先完成前端构建。浏览器保存流程应在数据库副本或虚构数据上测试，不能用真实账单做试写。

## 前端开发

前端使用 React、TypeScript 和 Vite，源码位于 `frontend/src/`。启用 `strict`、`noUncheckedIndexedAccess` 和 `exactOptionalPropertyTypes`；接口响应通过 Zod 在运行时校验，金额通过整数分传给后端。`make check-ui` 使用真正的 `tsc --noEmit`，不是只把 TypeScript 转译成 JavaScript；`make build-ui` 也会先进行同样的检查。

```sh
make install-ui  # 使用 package-lock.json 固定依赖
make build-ui
make serve DATABASE=data/accounting.sqlite3 PORT=8777
```

开发时另开终端运行 `make dev-ui`，监听源码并重新构建，再刷新浏览器查看；它不是 Vite HMR 开发服务器。所有界面和 API 仍由 Python 同源提供，保留本机访问与写入令牌校验，无需放宽 Origin 或 CSP。

构建产物位于 `accounting/static/dist/`，由 Git 忽略。前端未构建时服务会提示运行 `make build-ui`。部署到另一台机器需重新构建；如打包 Python wheel，先构建前端再打包，静态产物会随包附带。日常运行已构建的界面不需要 Node.js，也没有 CDN 或外部字体请求。

组件分工：`App.tsx` 管理导航与异步请求；`BillList.tsx` 管理列表和筛选；`ReviewPanel.tsx` 管理编辑草稿；`CategoryDialog.tsx` 管理分类；`shared.tsx` 展示原始来源和审计历史。`models.ts` 定义共享类型及响应校验，`api.ts` 负责本地接口边界，`format.ts` 处理金额与日期。测试只使用明确编造的数据。

`INPUT_DIR` 是账单文件夹；导入其顶层全部 `.csv`、`.xlsx` 和 `.pdf`，不递归扫描。数据库首次运行自动创建。也可以用 `make test PYTHON=/absolute/path/to/python3` 指定解释器。

一次导入先完整解析全部文件，再在一个事务内写入。无法识别的格式、坏行、工商银行逐页合计或余额连续性不符都会使本次导入失败。PDF 目前只支持已验证的工商银行十三列表格模板，不是通用银行 PDF 解析器。

运行结果保存在本机：

```text
data/
  accounting.sqlite3
  import-report-<batch-id>.json
```

报告包括文件哈希、来源行数、校验口径、新增/重复数量及数据库完整性检查。同源事件通过账户、外部交易 ID 和事件类型识别；相同快照重复导入不新增账单。没有可靠交易 ID 的银行卡记录使用保守的来源指纹和重复次数序号。外部 ID 只解决同源去重，不能单独解决美团、支付宝和银行卡之间的重复计算。

来源完整保存在 `raw_records`，含原始字段、原分类、文件哈希和首次来源位置；不再设置 `import_files`、`import_rows`。同源事件的新快照追加保存，不覆盖旧快照、人工修改或软删除决定。微信和美团导出没有稳定账户标识时默认归入 `personal` 档案；其他人的文件应使用独立 `--profile`，不能混入同一档案。

**导入不等于消费分析完成。** 首次导入的 `bills` 均为待核对记录，分类和使用日期为空，不进入已确认个人消费视图。保留完整文件，包括分析区间外的付款；后续再关联订单、支付与资金来源，核对资金性质及分类。支付宝声明支出可能采用扣除成功退款后的口径，报告分别保留原始支出合计和退款扣除后的对齐结果，不在导入时改写金额。

数据库可以直接只读查询；业务写入必须经过 `Database.batch` 提供审计上下文，普通 SQLite 客户端无法绕过上下文直接修改受保护表。`updates` 保存业务修改的前后快照及理由，`change_batches` 标识执行者和批次。原始来源、审计日志及批次不可修改或删除。

## 产品约定

- 浏览器访问本机运行的应用，由本地服务读写 SQLite。
- 原始记录保留来源；同一笔消费在订单、支付平台和银行卡中的记录只计算一次。
- 同时保留支付时间和可选的使用日期。使用日期由本人填写；未填写时沿用支付日期，并在 UI 标明默认值。AI 不推断使用日期。
- 支持自定义大类及可选小类，不设置“其他”。信息不足的记录进入待核对队列。
- AI 使用 LLM 对每一笔记录检查资金性质、消费分类及跨渠道关联。依据充分时自动修正，有歧义时交由本人核对；人工保存的修改受到保护，不以是否已经确认作为唯一保护条件。
- 修改分类、使用日期、个人承担金额或关联关系时，持久记录修改前后值、操作者、理由和证据。
- 垫付归还、退款和本人账户之间的资金移动分别处理。个人消费统计使用本人承担的净额。
- 年卡、多次课暂记为单笔，不做按月或按次分摊。
- 日常删除使用可恢复的软删除。永久清除是独立功能，后续实现时另行定义。

## 数据边界

公开仓库仅保存源代码、设计文档和明确编造的测试数据。原始账单、账户信息、SQLite 文件、AI 修改日志、截图、解析中间产物和备份只保留在本机。

建议将后续私有文件放入以下已忽略目录：

```text
data/
  imports/    原始账单
  db/         SQLite 数据库及其附属文件
  exports/    私人报表
  backups/    备份
  work/       PDF 页面、解析中间文件等
```

现有账单不必为了运行导入而移动。仓库也按扩展名忽略 CSV、Excel 和 PDF 文件；将来如需提交公开样本，应先制作完全虚构的 fixture，再明确调整相应忽略规则。当前测试只使用代码中编造的数据。

`.gitignore` 不会移除已经被 Git 跟踪的文件。每次提交仍须检查暂存区，避免提交个人数据。公开文档和截图中也不应包含真实交易、账户标识或本机私有路径。

提款或充值只能说明资金移动，不能据此还原之后的现金消费；如需纳入现金购买，必须手工补记实际用途和金额。文件日期覆盖完整，也不等于所有记录已经完成关联、分类或核对。

## 后续实现顺序
